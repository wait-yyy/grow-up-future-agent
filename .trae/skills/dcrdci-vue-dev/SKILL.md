# DCRCI Vue Development Skill

This skill defines the architecture, conventions, and business rules for the **dcrdci** project — an emotion-driven document generation application built with Vue 3 professional architecture.

---

## Tech Stack

| Layer | Technology |
|-------|-----------|
| Framework | Vue 3 + TypeScript (Composition API + `<script setup>`) |
| State | Pinia (setup store pattern with `defineStore('name', () => {})`) |
| Local DB | Dexie (IndexedDB wrapper) — `src/db/index.ts` |
| AI | OpenAI SDK (`openai` npm package, `dangerouslyAllowBrowser: true`) |
| Routing | Vue Router 5 |
| Build | Vite |

### Rules
- **NEVER** read API key from user input, localStorage, or settings store
- **NEVER** show an API Key input field in any UI
- **NEVER** check `settingsStore.settings.apiKey` before sending messages
- `ai.service.ts` imports `BUILTIN_API_KEY` from constants for the key
- `ai.service.ts` reads `model` and `baseUrl` from `useSettingsStore()` (with defaults)
- No "needSettings" flow — chat works immediately without any configuration
- SettingsModal only controls `defaultEmotions` (which emotion types to auto-generate)

### Correct ai.service.ts Pattern
```typescript

import { useSettingsStore } from '@/stores/settings'

function createClient(): OpenAI {
  const { settings } = useSettingsStore()
  return new OpenAI({
    apiKey: BUILTIN_API_KEY,
    baseURL: settings.baseUrl?.trim() || undefined,
    dangerouslyAllowBrowser: true,
  })
}
```

### Correct useChat.ts Pattern
```typescript
async function sendMessageAndReply(content: string) {
  // NO apiKey check — just send directly
  await chatStore.addMessage('user', content)
  chatStore.generating = true
  try {
    const result = await sendMessage(chatStore.messages, role, onDelta)
    await chatStore.addMessage('assistant', result)
    chatStore.generating = false
    autoGenerateDocs()
  } catch (e: any) {
    chatStore.generating = false
    setError(e?.message ?? '发送失败', 8000)
  }
}
```

## Component Conventions

### Script Setup Pattern
```vue
<script setup lang="ts">
import { computed, ref } from 'vue'
import type { SomeType } from '@/types'
import { SOME_CONST } from '@/constants'
import { someUtil } from '@/utils'
import SomeChild from '@/components/...'

const props = defineProps<{ ... }>()
const emit = defineEmits<{ ... }>()
</script>
```

### Props & Emits
- Always use TypeScript generic syntax: `defineProps<{ ... }>()`, `defineEmits<{ ... }>()`
- Emits use tuple syntax: `emitName: [arg1: Type, arg2: Type]`

### Style Rules
- **Always `<style scoped>`** — never global styles in components
- Use CSS variables from `variables.css` — never hardcode colors/spacing
- `color-mix()` for opacity variants
- Transitions: `var(--transition-fast)` (= 0.15s ease)
- Border radius: `var(--radius-sm/md/lg/xl)`
- Dark theme by default (bg-primary: #0f0f0f, text-primary: #e5e5e5)

### Modal Pattern
- Use `AppModal` as wrapper: `<AppModal :visible :width @close>`
- Modal structure: `modal-header` → `modal-body` → `modal-footer`
- Use `<Teleport to="body">` (handled by AppModal)

## Store Conventions

### Setup Store Pattern
```typescript
export const useXxxStore = defineStore('xxx', () => {
  const items = ref<Type[]>([])
  const filtered = computed(() => items.value.filter(...))

  async function load() { items.value = await db.xxx.toArray() }
  async function create(data: ...) { await db.xxx.add(record); items.value.push(record) }
  async function update(id: string, data: Partial<Type>) { await db.xxx.update(id, data); ... }
  async function remove(id: string) { await db.xxx.delete(id); items.value = items.value.filter(...) }

  return { items, filtered, load, create, update, remove, ... }
})
```

### Store Rules
- All stores use setup function syntax (not options API)
- Dexie `db` is the single source of truth for persistence
- `ref()` for state, `computed()` for derived state
- Always `await db.xxx.operation()` before updating local ref
- Settings store uses `localStorage` (not Dexie) — only stores `defaultEmotions`
- Never import stores into each other circularly; use composables to coordinate

## Service Conventions

```typescript
// services/ai.service.ts
import OpenAI from 'openai'
import { BUILTIN_API_KEY } from '@/constants'
import { useSettingsStore } from '@/stores/settings'
import type { ... } from '@/types'

function createClient(): OpenAI {
  const { settings } = useSettingsStore()
  return new OpenAI({
    apiKey: BUILTIN_API_KEY,
    baseURL: settings.baseUrl?.trim() || undefined,
    dangerouslyAllowBrowser: true,
  })
}

export async function sendMessage(...): Promise<string> { ... }
export async function generateDocument(...): Promise<...> { ... }
export async function generateAllDocuments(...): Promise<...> { ... }
```

### Service Rules
- Services are stateless functions — no reactive state
- `createClient()` uses `BUILTIN_API_KEY` for auth, reads `baseUrl`/`model` from settings store
- API Key always comes from `BUILTIN_API_KEY` constant — never from user input
- `model` and `baseUrl` are read from `useSettingsStore()` with sensible defaults
- Business logic (when to call, what to do with results) belongs in composables, not services

## Composable Conventions

```typescript
// composables/useXxx.ts
export function useXxx() {
  const store = useXxxStore()
  const { errorMsg, setError } = useError()

  async function doSomething() {
    try { ... }
    catch (e: any) { setError(e?.message ?? '操作失败') }
  }

  return { errorMsg, doSomething }
}
```

### Composable Rules
- Composables coordinate between stores and services
- They handle error display via `useError()`
- They do NOT contain UI markup — that belongs in components
- `useChat` is the main orchestrator: sends message → gets reply → auto-generates docs
- **NO apiKey check before sending** — built-in key is always available
- `autoGenerateDocs()` is fire-and-forget (does not block next message)

## Business Domain Rules

### Core Concepts

1. **Role (角色)** — An AI persona defined by `systemPrompt` + `emotionOverrides`
   - Default: empty list, user creates all roles manually
   - No built-in roles — `isBuiltin` field exists but not used
   - All roles are deletable
   - Stored in Dexie `roles` table
   - Chat works WITHOUT a role — no role means no systemPrompt injected

2. **Document (文档)** — An AI-generated personality/trait document in a specific emotion style
   - Documents ARE personality prompts — they represent behavioral traits
   - Auto-generated after each chat reply (one doc per emotion type)
   - Stored in Dexie `documents` table
   - Status flow: `pending` → `kept` / `discarded`

3. **Fusion (融合)** — Merging a document into a role creates a NEW role with combined personality
   - If no current role: creates a new role with doc content as systemPrompt
   - If current role exists: creates a new role with combined prompt
   - Original role is preserved — fusion always creates a new role

4. **Emotion (情绪)** — Six types: objective, enthusiastic, melancholic, humorous, critical, poetic
   - Each has a label, color, and default system prompt in `constants/`
   - Roles can override specific emotion prompts via `emotionOverrides`

5. **Chat** — Main interaction area
   - Sessions with tab-based navigation
   - Streaming AI responses with cursor indicator
   - Auto-triggers document generation after each assistant reply (fire-and-forget)
   - Works immediately — no setup required (built-in API key)

### Data Flow

```
User sends message
  → ChatPanel emits 'send'
  → DefaultLayout calls useChat().sendMessageAndReply()
  → chatStore.addMessage('user', ...)
  → ai.service.sendMessage() with streaming (uses BUILTIN_API_KEY)
  → chatStore.addMessage('assistant', result)
  → autoGenerateDocs() [fire-and-forget]
  → ai.service.generateAllDocuments() (parallel per emotion)
  → docStore.addDocuments()
```

## Settings Store

The settings store manages `model`, `baseUrl`, and `defaultEmotions`.

```typescript
interface Settings {
  apiKey: string        // Not used — BUILTIN_API_KEY is always used instead
  baseUrl: string       // API base URL, default '' (OpenAI official)
  model: string         // Model name, default 'gpt-3.5-turbo'
  defaultEmotions: EmotionType[]  // Which emotion types to auto-generate
  generateTimeout: number
}
```

- `apiKey` field exists for type compat but is NEVER used — `BUILTIN_API_KEY` constant is always used
- `baseUrl` and `model` are read by `ai.service.ts` with defaults
- `defaultEmotions` controls which emotion docs to auto-generate
- **Do NOT add API Key field to any UI** — it's built-in

## When Adding New Features

1. **New type** → add to `types/index.ts`
2. **New constant** → add to `constants/index.ts`
3. **New DB table** → add to `db/index.ts` with new version
4. **New store** → create `stores/<name>.ts` following setup pattern
5. **New service** → create `services/<name>.service.ts` (stateless, uses BUILTIN constants)
6. **New composable** → create `composables/use<Name>.ts` (coordinates stores + services)
7. **New component** → place in `components/<feature>/` or `components/common/`
8. **New CSS variable** → add to `assets/styles/variables.css` only
9. **New route** → add to `router/index.ts`, create view in `views/`

## Error Handling Pattern

```typescript
// In composables:
const { errorMsg, setError } = useError()

try { ... }
catch (e: any) {
  setError(e?.message ?? '操作失败', 8000)
}
```

- `useError()` provides `errorMsg` ref and `setError(msg, duration?)`
- Error bar displayed in DefaultLayout when `errorMsg` is non-empty
- Auto-clears after duration (default 5000ms)
- **NO `API_KEY_MISSING` special case** — key is always available
